Two defects the batch exposed

The reference could never grow with the corpus

output/bindingdb/our_patents.tsv was hardcoded in value_check and reference_bench, and output/ is frozen v1, read-only. The ten new patents therefore had zero reference rows — and reference_bench skips a patent whose reference set is empty (if not ref_all: continue). A new batch scored not "0% coverage" but nothing at all, silently, while corpus totals looked unchanged. Now config.BDB_REFERENCE_TSV, preferring a writable copy under OUTPUT_DIR and falling back to the frozen path.

PATENT YIELDED NOTHING could be silenced by cell formatting

The denominator required a cell to be a bare number. US10266548 answered shaped=0 while holding 1,049 numeric cells and extracting 242 records — its values carry the unit inline (12.3 nM). 197 reference compounds went unreported by the one check that is supposed to be unsuppressable — the same defect class the check exists to catch, one level in.

Now "short cell containing a digit". Breadth is safe because the condition is conjunctive: it only matters when the patent produced zero usable measurements. Over 83 patents, widening it adds exactly one — the one it was missing.

Caveats

  • Coverage here is compound-id overlap, not value correctness. The value-agreement check (value_check) has not been run on batch 3.
  • --patch (the capability tier) was not run. US9265734 and US10266548 both look like capability gaps rather than layout gaps, so the rule tier was never going to fix them.
  • BindingDB is not a gold standard. Only single-patent-attributed rows are counted, but it still cites example numbers patents do not contain, and the two id-mismatch patents may be that rather than our error.
