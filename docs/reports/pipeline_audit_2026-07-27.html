PatentMoleculeDB · Pipeline Audit

Two systems wearing one coverage number

Measured across the 22 patents currently in output_v2. The pipeline reports 97.6% structure coverage. Verified against BindingDB, the route supplying two thirds of that coverage is correct 0.2% of the time.

The stated purpose is "every named compound's IUPAC, from the patent." For half the corpus the system is functioning as a Google Patents mirror with a PubChem name lookup attached. The 97.6% coverage figure measures how often Google had an answer — not how often we were right.

Accuracy by extraction route

Diagnosing the 65%

A low score could mean wrong chemistry, or right chemistry attached to the wrong compound ID. Those are different bugs with different fixes, so we separated them across the 1,041 checkable gp_embedded_meta records.

Root cause, identified

The bridge's positional fallback accepts a match when MS [M+H]⁺ agrees within ±5 Da. At drug-like weights (300–600 Da) that is roughly 10,000–17,000 ppm — wide enough for many different analogs and isomers to pass. That is exactly the mechanism that produces right-chemistry-wrong-label.

Correct practice is regime-aware: 5–20 ppm when the patent reports HRMS with decimals, ±0.3–0.5 Da for unit-resolution LC-MS. Switch on whether decimals are present. This is the smallest diff on the roadmap aimed at the largest identifiable error class.

This is not just our problem

IBM's PatCID study (Nature Communications, Aug 2024) benchmarked molecule retrieval across five systems on a random patent sample. Google Patents is independently known-weak — and every automated patent-chemistry system is mediocre.

SureChEMBL's own team invalidated 172,504 previously-registered compounds during its May 2025 overhaul. An independent audit found it recovers ~59–61% of what a human curator finds, falling to ~12% once false positives are counted.

So we keep extracting ourselves

There is no external source to simply consume instead — and critically, none of them carry assay values at all, which is half the deliverable. Our own text-reading routes at 45–71% are competitive with the best systems in that table. The problem isn't that we extract badly; it's that we blend good extraction with bad extraction and report the mixture as one number.

Failure modes in the code

The pipeline hangs for 30 minutes by default — confirmed live

Running one patent during this audit, the process sat at 0.0% CPU for 11 minutes (15s CPU consumed) before being killed. With LLM_BATCH=1 (the default) it submits a Message Batch, then polls every 15s against a 1800-second timeout, reporting progress only through buffered logger calls. Any cache-miss run looks like a hard freeze.

Every LLM call is sampled at temperature 1.0, then cached forever

temperature is never set anywhere, so the API default of 1.0 applies. Combined with the response cache, one random draw becomes the pipeline's permanent answer. Reruns are not reproducible; the first sample wins by accident.

The image cache key collides — confirmed empirically

The cache hashes only the first 1KB of the base64 image. Testing all 412 crops on disk, two genuinely different images already share a key — the second silently inherits the first's SMILES. Low volume, but silent structural corruption is the worst kind.

Failures are indistinguishable from empty patents

101 except Exception handlers, 31 silent, and 217 sites returning empty on failure. US20240010684A1 produced zero compounds alongside 166 assay values and exited cleanly. US11312727 produced 6 compounds against 614 assay values. Nothing registers these as problems.

Structural

process_patent.py is 2,009 lines, and _bridge_gp_to_harvest_cids — the riskiest logic in the system and the confirmed source of the 19.9% — is a single 346-line function. Outputs are written non-atomically. There is no checkpointing: a failure at minute 25 discards everything.

The biggest available win

Stop OCR-ing documents that are already structured

USPTO publishes its own full-text XML with real table markup. The Patent Grant ICE DTD imports the OASIS/CALS table model (tgroup/row/entry) — the same standard as DocBook. For any 2001+ patent the assay tables are available as genuine row/column XML, free and public domain.

This dissolves the reason MinerU exists here. Every corruption class we compensate for — <|ref|> tags, bbox pollution, mid-IUPAC line wraps, 2-y1} for 2-yl}, merged rows — simply does not arise. Docling ships a uspto_backend that parses it (MIT; pin ≥2.74.0, earlier versions carry an XXE vulnerability in exactly that parser).

Verified from here: bulkdata.uspto.gov is dead (DNS failure), api.uspto.gov is live and returns 401 without a key. A free account is required, and table fidelity is unconfirmed until someone tests it — that test gates the whole recommendation.

Recommended order of work

Tier 0 — stop the bleeding (hours)

  1. Set temperature=0 on every LLM call.
  2. Hash the full image in the cache key, not the first 1KB.
  3. Put a lock around cost_tracker.record() — it does unlocked read-modify-write on spend while a 10-worker pool makes paid calls, so the caps under-enforce.
  4. Make the batch poll emit unbuffered progress; default LLM_BATCH=0 for interactive runs.
  5. Write outputs atomically (temp file + os.replace).

Tier 1 — make failure visible (days)

  1. A patent yielding 0 compounds but non-zero assay values must raise, not return cleanly.
  2. Replace the 31 silent except blocks with logged, counted failures surfaced in route_audit.json.
  3. Stop reporting one blended coverage number — 9,008 records carry no iupac_source at all.

Tier 2 — the accuracy fix (weeks)

  1. Get a USPTO key and test table fidelity on 3 known-hard patents. This single experiment decides the ingestion strategy — and it is about a day of work.
  2. Tighten the MS tolerance from ±5 Da to regime-aware ppm / ±0.5 Da.
  3. Turn on the unused OPSIN flags (allowUninterpretableStereo especially) and add deterministic line-join repair, letting OPSIN itself be the acceptance oracle. Free accuracy in the routes already measured most accurate.
  4. Add the formula / MS-mass / InChIKey validation layer; require the LLM-cleaned name and the LLM-direct SMILES to agree by InChIKey before trusting either. We already generate both and never compare them.
  5. Decide what gp_embedded_meta is for — 65% of the corpus at 0.2% verified accuracy. Demote to corroboration-only, gate it behind validation, or drop it.
  6. Build a 20–50 patent golden set; run metamorphic regression through process_patent() itself, not a bypassing eval script.

Tier 3 — only afterwards

  1. The image route, behind a two-model-agreement gate. Calibrate to reality: PatCID reaches ~45–55% precision on unfiltered patent images, not the 90%+ of method papers.
  2. Markush stays out. IBM excludes it from PatCID entirely, stating there is no reliable approach at scale. Holding markush/ out of the orchestrator was correct.
